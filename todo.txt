messages that made the changes, not kept here.  Checks that need a person at a

so a session on another OS can see at a glance what it can pick up.

it from c750678, and the v1.37 .deb ships web/romwbw.html, romwbw.js,

- [BROWSER] the wasm's video, DSKY, sound and printer callbacks are wired to
names nothing implements.  emu_io_wasm.cc emits Module.onVideo*, Module.onDsky*
and Module.onPrinterOutput; romwbw.html-template implements Module.onVda* and
Module.onSnd*.  renaming one side does not switch it on: there is no sound
emitter in the core at all, five of the eight onVda* handlers have no
counterpart, and onVdaWriteChar takes an attribute byte the emitter never
sends.  about 200 lines on each side that have never executed - wire it
properly behind a browser, or delete one side.

- [EMSCRIPTEN] the web Boot field never reads NVRAM back.  the page pushes the
string with _romwbw_set_boot_string and clears it with _romwbw_clear_nvram, and
web/makefile's EXPORTED_FUNCTIONS holds no getter, so a boot target the guest
itself writes with SYSCONF is lost on reload - the text survives only in
localStorage.  the CLI has load_nvram_setting/save_nvram_setting under
$XDG_CONFIG_HOME/romwbw_emu/nvram and the web build has no equivalent read
path.  needs emcc to build and a browser to check.

- [EMSCRIPTEN] R8's "Reading:" line names the file that was really opened on
the CLI only.  emu_host_file_get_read_name() returns "" in emu_io_wasm.cc on
purpose - a browser read is a file PICKER, so the guest's string is a hint the
user is free to ignore - and the comment there carries the whole argument.
changing it needs a name parameter on emu_host_file_provide_data() and a change
to the page's picker callback.  until then the browser answers 0xFF and R8
prints what was typed, which is what it always did.

- [RELEASE] the hd1k_* disk images published under ioscpm's v1.4.5 tag still
carry the old R8/W8, and all three ports pin that tag (RELEASE_TAG in z80cpmw's
DiskCatalog.cpp and in cpmdroid's DiskCatalogRepository.kt, releaseTag in
ioscpm's EmulatorViewModel.swift).  19 of disks.xml's 21 entries exist nowhere
in this tree.  a user coming through any of them gets a W8 that truncates every
binary at the first 1Ah and an R8 that can erase files it did not create.
steps 0 through 3 of docs/RELEASE_ORDER_2026-08-25.md are cleared - c750678 set
step 2's and step 3's headings to "Code done", z80cpmw's 713bfce having defined
emu_host_file_get_read_name() so that port links again - so what is left is
step 4 - rebuild with disks/rebuild_disk_utils.sh and publish under a NEW
tag - and then step 5's per-port pin bump.  read that document's second hazard
before step 5: bumping disks.xml's version attribute deletes the user's disks.
measured 2026-09-01 against the published asset rather than assumed: v1.4.5's
hd1k_combo.img (51380224 bytes, sha256 be19984e...) carries a 1280-byte w8.com
that rebuilds byte for byte from w8.asm at 3101b6d - `cp 1Ah` still in the copy
loop, usage string without `[hostpath]`, and the `06 e9 cf` interlock probe
absent - and a 1079-byte r8.com older than any build in this repo's history,
with no illegal-character table.  the other 19 published images were not
dissected.
what would make this catchable rather than periodic: two different disks.xml
files are in play and only one of them has checksums.  this tree's
disks/disks.xml is `<disks version="6">`, 21 entries, no per-disk version or
checksum, so nothing here can look at a release asset and tell whether its
w8.com is current.  the catalog the three ports actually fetch is ioscpm's,
`<disks version="13">`, 20 entries, and it DOES carry a per-disk sha256 - and it
is that file's version attribute whose bump fires the disk-wipe hazard.

- [MAC/LINUX] the last integer-narrowing warnings in a clean build are not this
repository's to fix.  qkz80_MK_INT16 in cpmemu's qkz80_types.h builds an int
and hands it to a qkz80_uint16 parameter, so qkz80_reg_pair.h is reported twice
by every object file that calls set_low()/set_high() - 8 warnings from
`make -C src all`, 12 with the test programs, none of them actionable from
here.  the fix is a qkz80_uint16() around that macro body, in cpmemu, after
which CPMEMU_REF has to move past it in both workflows and in release.yml.
until then a clean build is not silent, which is the state that teaches people
to stop reading warnings.  measured again 2026-09-01 against cpmemu v4.7.2
(91151f1), the ref v1.37 pins: same 8 and 12, all of them qkz80_reg_pair.h:32
and :35.  the pin moving in v1.37 does not touch this - `git diff 9a94e8d
91151f1 -- 'src/qkz80*.h' 'src/qkz80*.cc'` is empty, so the macro is byte for
byte what it was.  z80cpmw's C4267 suppression on hbios_dispatch.cc is
removable either way: 8eeb227 cast all six sites here, so the file is clean at
/W3 from v1.37 on.  it has NOT been removed there - checked 2026-09-01 at
z80cpmw 148be4f, still present at z80cpmw/z80cpmw.vcxproj:260.  grep for the
MSBuild spelling `<DisableSpecificWarnings>4267`, not for `/wd4267`; searching
for the compiler flag reports it gone when it is not, which is how this entry
nearly got deleted as stale.
