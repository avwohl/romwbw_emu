Todo list.  Open items only - finished work is in CHANGELOG.md and in the commit
messages that made the changes, not kept here.  Checks that need a person at a
keyboard are in MANUAL_CHECKS.md.

Every item carries a tag saying what a machine has to be able to do to take it,
so a session on another OS can see at a glance what it can pick up.

- [BROWSER] no browser has drawn the page since xterm was vendored, since a
zero-byte export started downloading, and since the download name became the
lowercased last component of the typed path.  the checklist is in
MANUAL_CHECKS.md.  it needs a wasm built elsewhere: emcc is not on this
machine, so nothing here can rebuild web/romwbw.js.

- [BROWSER] the wasm's video, DSKY, sound and printer callbacks are wired to
names nothing implements.  emu_io_wasm.cc emits Module.onVideo*, Module.onDsky*
and Module.onPrinterOutput; romwbw.html-template implements Module.onVda* and
Module.onSnd*.  renaming one side does not switch it on: there is no sound
emitter in the core at all, five of the eight onVda* handlers have no
counterpart, and onVdaWriteChar takes an attribute byte the emitter never
sends.  about 200 lines on each side that have never executed - wire it
properly behind a browser, or delete one side.

- [EMSCRIPTEN] the web Boot field never reads NVRAM back.  the page pushes the
string with _romwbw_set_boot_string and clears it with _romwbw_clear_nvram, and
web/makefile's EXPORTED_FUNCTIONS holds no getter, so a boot target the guest
itself writes with SYSCONF is lost on reload - the text survives only in
localStorage.  the CLI has load_nvram_setting/save_nvram_setting under
$XDG_CONFIG_HOME/romwbw_emu/nvram and the web build has no equivalent read
path.  needs emcc to build and a browser to check.

- [EMSCRIPTEN] R8's "Reading:" line names the file that was really opened on
the CLI only.  emu_host_file_get_read_name() returns "" in emu_io_wasm.cc on
purpose - a browser read is a file PICKER, so the guest's string is a hint the
user is free to ignore - and the comment there carries the whole argument.
changing it needs a name parameter on emu_host_file_provide_data() and a change
to the page's picker callback.  until then the browser answers 0xFF and R8
prints what was typed, which is what it always did.

- [DECISION] --escape=none gives the guest every key and gives up sim>
altogether: console_escape_char is 0, and check_console_escape_async(),
poll_stdin() and emu_console_check_escape() all take their early-out.  the
alternative on the table is a doubled escape char - one press reaches the
guest, two in a row reach sim> - which costs a pending-escape state and a rule
for delivering a lone escape late, in a function DOWNSTREAM.md makes a contract
three ports keep.  nobody has asked for it.  decide it or delete this item.

- [DECISION] LST:, PUN: and RDR: are aliased to the console, and the whole
aux/printer family (emu_printer_set_file, emu_printer_out, emu_printer_ready,
emu_aux_set_input_file, emu_aux_set_output_file, emu_aux_in, emu_aux_out) has
no caller anywhere and no flag to reach it.  measured under CP/M 2.2 on
hd1k_combo.img: STAT DEV: reports LST: is LPT: and PUN: is PTP:, and
PIP LST:=SOURCE.TXT prints on the terminal - because SYSGET_CIOCNT answers 1,
so CBIOS has one character device to assign all four names to.  wiring
emu_printer_out() up is not "add a flag": it means answering 2 and routing CIO
unit 1, which MOVES LST: and PUN: off the console for everyone using it today.
owner's call - a real second device, or delete the seven functions.

- [DECISION] emu_console_write_char() drops CR and masks every output byte to
0x7F, in emu_io_cli.cc and identically in emu_io_wasm.cc.  so a progress line
never redraws - "100%\rDONE" arrives as "100%DONE" - and 0xC3 0xA9 arrives as
C ), a different printable character rather than a mangled one.  changing it is
cross-cutting: a piped run would gain CR LF where it yields bare LF today, so
every captured transcript and every script that greps the output changes; the
page's Module.onConsoleOutput rewrites LF to CR LF specifically to undo the
drop, so the two have to move in one commit or xterm gets CR CR LF; and
romwbw-debug.html has its own handler.  the 0x7F mask is a separate question
with a recorded reason (WordStar sets bit 7 on the last character of a word and
expects a dumb terminal to strip it), against which stands every guest that
draws a box or writes a national character.

- [DECISION] what a package ships, both halves of it.  the four ROM files in
this tree are one file - web/emu_avw.rom, web/emu_romwbw.rom, roms/emu_avw.rom
and roms/emu_romwbw.rom all md5 to 826c3bcf7db18a36f8eb73792873613d - so
deduplicating them means deciding which name is canonical and what the web
build fetches, since the page's ROM select offers emu_avw.rom by name.  and no
.img is staged by release.yml or by web/makefile's deploy targets, so a stock
deb or rpm has no disk at all, while the page offers five disk names of which
z80cpm_tools.img exists nowhere in this tree.  a 49 MB combo image in a deb is
a packaging decision; one answer covers both halves.

- [DECISION] emu_host_file_open_write() returns true unconditionally on every
buffering backend (browser, iOS, Android, and z80cpmw's deferred write), so a
path that cannot be created is only discovered at close - and W8 then prints
"Host file close failed - file may be truncated" for a file that was never
opened.  emu_io.h's contract now says that is allowed and that close is where
the real answer comes from.  making W8's two messages tell the cases apart
needs a distinguishable status from close, which changes the HBF_HOST_* return
codes four ports implement: a cross-port ABI decision, not a local edit.

- [DECISION] a config-file `boot` key is still written back to the nvram file
at exit, while a --boot on the command line applies to that run only.  that is
deliberate - romwbw_emu.json IS a persisted choice, so writing it through is at
worst redundant - and worth a second look if anything starts generating that
file per run.  --boot=none likewise names a pre-XDG setting in ~/.config and
leaves it in place, rather than reaching outside the config directory the run
selected.

- [RELEASE] the hd1k_* disk images published under ioscpm's v1.4.5 tag still
carry the old R8/W8, and all three ports pin that tag (RELEASE_TAG in z80cpmw's
DiskCatalog.cpp and in cpmdroid's DiskCatalogRepository.kt, releaseTag in
ioscpm's EmulatorViewModel.swift).  19 of disks.xml's 21 entries exist nowhere
in this tree.  a user coming through any of them gets a W8 that truncates every
binary at the first 1Ah and an R8 that can erase files it did not create.
steps 0 and 1 of docs/RELEASE_ORDER_2026-08-25.md are cleared, so what is left
is step 4 - rebuild with disks/rebuild_disk_utils.sh and publish under a NEW
tag - and then step 5's per-port pin bump.  read that document's second hazard
before step 5: bumping disks.xml's version attribute deletes the user's disks.
what would make this catchable rather than periodic: disks.xml carries no
per-disk version or checksum, so nothing here can look at a release asset and
tell whether its w8.com is current.

- [MAC/LINUX] the last integer-narrowing warnings in a clean build are not this
repository's to fix.  qkz80_MK_INT16 in cpmemu's qkz80_types.h builds an int
and hands it to a qkz80_uint16 parameter, so qkz80_reg_pair.h is reported twice
by every object file that calls set_low()/set_high() - 8 warnings from
`make -C src all`, 12 with the test programs, none of them actionable from
here.  the fix is a qkz80_uint16() around that macro body, in cpmemu, after
which CPMEMU_REF has to move past it in both workflows and in release.yml.
until then a clean build is not silent, which is the state that teaches people
to stop reading warnings.  measured again 2026-09-01 against cpmemu v4.7.2
(91151f1), the ref v1.37 pins: same 8 and 12, all of them qkz80_reg_pair.h:32
and :35.  the pin moving in v1.37 does not touch this - `git diff 9a94e8d
91151f1 -- 'src/qkz80*.h' 'src/qkz80*.cc'` is empty, so the macro is byte for
byte what it was.  z80cpmw's C4267 suppression on hbios_dispatch.cc is
removable either way: 8eeb227 cast all six sites here, so the file is clean at
/W3 from v1.37 on.  it has NOT been removed there - checked 2026-09-01 at
z80cpmw 148be4f, still present at z80cpmw/z80cpmw.vcxproj:260.  grep for the
MSBuild spelling `<DisableSpecificWarnings>4267`, not for `/wd4267`; searching
for the compiler flag reports it gone when it is not, which is how this entry
nearly got deleted as stale.

- [WINDOWS] nothing on Windows is RUN, only compiled.  the msvc job builds the
three core .cc files z80cpmw pulls straight out of src/ and stops there: there
is no MSVC build of the emulator to link and no test program that would run.
z80cpmw's own CI is still the only thing that executes Windows code, and
cpmemu's suite still skips its two Windows cases for want of a machine.
