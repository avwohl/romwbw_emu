- [ANY] DELETE THE RELEASE GATE.  ROMWBW_SUPPORTED_RELEASES gates ROM loading on
the RomWBW release number, which is the HBIOS-to-disk-image axis and none of this
core's business.  What this core actually depends on is three things and the
release number is not one of them: the two ports at src/emu_hbios.asm:38-39, the
function set in src/hbios_dispatch.cc, and the hardcoded 0x0406 in HBX_BNKCALL
(:336-365).  romwbw_disks already versions the first two as interface v0, and the
third belongs in the romwbw_ver.inc its build generates.  Because of this macro,
INTERFACE_V0.md's "Adding RomWBW 3.7.0 is a new release tag and a regenerated
index - no client change, no interface bump" is false: a 3.7.0 entry is discarded
by every client, and emu_validate_rom_hcb refuses the ROM at load
(src/emu_init.cc:194-211) even with the client filters gone.  So publishing 3.7.0
costs a release of Windows, macOS, iOS, Android and Linux, which is the coupling
romwbw_disks was built to remove.  Note also that the release bytes this macro
adjudicates are written by romwbw_disks' own tools/build_rom.sh, which generates
romwbw_ver.inc and stamps the HCB at 0x105 - the number is written there and
judged here, with nothing keeping the two in step but a person editing a macro.
  What comes out, in what order, and what it costs is docs/RELEASE_GATE.md.  It
also takes emu_romwbw_release_supported, emu_romwbw_supported_list,
emu_set_allow_untested_romwbw / emu_allow_untested_romwbw,
--allow-untested-romwbw, roms/verify_romwbw_pin.sh and its step in
.github/workflows/test.yml, and in tools/romwbw-get the _runnable() filter, the
--allow-untested and --assume-supported flags, and the default of `mirror
--versions` - three flags and a function, not the "four flags" this item used to
say.  ROMWBW_DEFAULT_* stays: it is a build input and a fallback, not a
constraint on loading.
  IT ALSO TAKES A CROSS-REPOSITORY PROTOCOL, which is what this item and
docs/RELEASE_GATE.md's "what comes out" both missed.  emu_romwbw_supported_list()
is printed as the second line of print_version_banner (src/romwbw_emu.cc:806-811),
and tools/romwbw-get:389-393 calls that line a protocol with three consumers: its
own RE_RUNS (:395), roms/verify_romwbw_pin.sh, and romwbw_disks'
tools/boot_test.sh.  `romwbw-get mirror` then copies the answer into
catalog/manifest.json as emu_supported, which web/romwbw.html-template:948-952
reads - so the page's release select goes with it, and the [EMSCRIPTEN] item
below about exporting that same function to the wasm is not separate work, it is
a fourth consumer this would delete.  Whoever takes either one should read both.
  THE BLOCKER IS NOT THE ONE THIS ITEM NAMED.  boot_test.sh is already a required
publish step: romwbw_disks docs/RELEASING.md:825 makes it a checklist item and
closes the obvious hole itself - "A SKIP line means no emulator was found, which
is not a pass" - and :441-447 already orders `boot_test.sh 3.7.0` before the X()
line is added here.  It is required by the written procedure and by no script:
neither publish_release.sh nor verify.yml runs it.  The real blocker is that
boot_test.sh CONSUMES THE GATE.  It asks the binary which releases it can run
(:85-98); with that banner line deleted RUNS is empty, the pre-v1.39 "RomWBW
compatibility: v..." fallback is empty too, and it die()s - exit 1, not a skip.
Cut the gate first and the publish-time gate does not lose a fact, it FAILS, and
every publish is blocked until boot_test.sh is changed to test every published
version unconditionally and to drop its refusal branch (:210-218), whose failure
message names emu_validate_rom_hcb.  So step 1 of docs/RELEASE_GATE.md's order of
work is that change to boot_test.sh, not the checklist line that is already
there.
  TWO THINGS IT STILL DOES NOT FIX, both from the note.  v0's pillar 3 covers the
private 0xE1-0xEA block and two standard functions, not the whole dispatcher
surface - so a release whose CBIOS calls a standard function this core lacks is
exactly the risk the allowlist stands in for, and v0 as written does not catch
it.  And 0x0406 should ride along with the next bank-0 change rather than be cut
on its own, for the generation cost the emu_hbios.asm item below spells out.

- [ANY] The stored romwbw_version in catalog.json can differ, durably and
silently, from the release every run actually uses.  save_choice writes it to
$XDG_CONFIG_HOME/romwbw_emu/catalog.json (tools/romwbw-get:175-185) and cmd_use
(:1107) is its only writer; resolve_version (:616-619) then falls through to the

file and without saying anything.  So `romwbw-get use 3.5.1` followed by an index
that stops offering 3.5.1 leaves catalog.json naming 3.5.1 for ever while every
run fetches and boots something else.  It surfaces only in `versions --json` as
"selected" (:1003-1005); the plain listing marks "selected" only on rows it
prints (:1019-1020), so a filtered-out entry shows nothing at all.
  THE DAMAGE IS SMALL AND THAT IS WHY THIS IS NOT URGENT.  One resolved version
feeds every asset path - Catalog.scoped (:467-469), assets_dir (:693),
working_copy (:931-943) - and cmd_run fetches the ROM and both disks for that
same version (:1152-1175), so unlike the GUI ports a ROM and images from
DIFFERENT releases cannot be assembled here.  What is wrong is the silence, not
the pairing.
  Nor is this z80cpmw's bug, which was filed there on 2026-09-17 after measuring
a machine with 3.6.0 stored against two -v0-3.5.1 disks.  That one turns on a
back-fill that corrects only an EMPTY stored value; the reconciliation here is
the inverse, running on a non-empty one (`if stored and any(...)`, :613-614).
Nothing in this repo derives a release from a filename at all: the only release
readers are emu_romwbw_release_of_image (src/emu_init.cc:57-67) and
emu_romwbw_release_loaded (:69-81), and both read HCB bytes out of ROM content.
  Two reachability notes for whoever takes it.  _runnable() (:1417-1436) returns
None - warning once and filtering NOTHING - when no romwbw_emu binary is found,
when the binary reports no list, or under --assume-supported, and cmd_run passes

unchecked.  And `romwbw-get use --index-url URL` with no version argument stores
a new index_url and validates nothing against it (:1105-1106), which is the
easiest way to end up pointing at an index that has never heard of the release

generation-2 republish of both 3.5.1 and 3.6.0.  budget it before the next
emu_hbios.asm change.  the finished HB_BNKCALL work is CHANGELOG.md's `### HB_BNKCALL performs a real
bank call` section (grep it; CHANGELOG grows at the top, so a line number will

- [EMSCRIPTEN] the page decides which RomWBW releases it can boot from a value
recorded at mirror time, not by asking the core it is running.  `romwbw-get
mirror` runs the CLI binary's --version and writes the answer into
catalog/manifest.json as emu_supported; the page disables anything outside that
list.  so the two can disagree - a mirror written by one build, served next to a
wasm compiled from another - and the page would then offer a release the wasm
refuses, or grey out one it would run.  the honest source is
emu_romwbw_supported_list(), which already exists in src/emu_init.h and
src/emu_init.cc, and emu_init.cc is already in web/makefile's ROMWBW_SRCS, so
this is one name added to EXPORTED_FUNCTIONS plus a few lines in the page.  it
was not done because it cannot be built or checked without emcc, which is absent
here, and shipping an untested export is worse than the mismatch it fixes.
tagged [EMSCRIPTEN] rather than [ANY] for that reason.
what makes it worth doing rather than merely correct: the whole point of the
mirror is that re-running it publishes a newly released disk with no wasm
rebuild.  the moment somebody re-mirrors without rebuilding - which is the
intended workflow, not an accident - emu_supported is a fact about a binary that
is no longer the one in the page.  do it the next time emcc is on the machine.
  BUT READ THE DELETE-THE-RELEASE-GATE ITEM FIRST.  it proposes deleting
emu_romwbw_supported_list() outright, along with the banner line this mirror

not independent: if the gate goes, this one does not move to a better source,
it evaporates - there is no list to export and nothing for the select to grey
out.  whichever is taken first decides whether the other exists at all.

- [SOUND] the SND handler stores four channels and plays one beep.  handleSND
in src/hbios_dispatch.cc keeps snd_period[4] and snd_volume[4], and
BF_SNDQUERY/SNDQ_CHCNT answers "4 tone channels, 0 noise" - but nothing reads
those arrays back out.  BF_SNDPLAY looks at channel 0 only and calls
emu_dsky_beep(duration), which is a fixed beep of that length: the period is
not a pitch and the other three channels are inaudible.  a guest playing a
four-voice tune hears four identical beeps in sequence.  SNDQ_DEV already
declines to name a chip for exactly this reason - "there is no sound chip here
- nothing reads snd_period or snd_volume back out".
  WHAT WOULD CLOSE IT is rendering the channels the handler already records:
period -> frequency, volume -> amplitude, mixed across the four.  that is one
AY-3-8910/YM2149 worth of square-wave generation and it belongs here, in the
shared core, not in any one front end - all four ports would get it from the
same change, and only the output side (AudioTrack, AVAudioEngine, WASAPI, Web
Audio) is per-client.
  IT NEEDS A NEW emu_io ENTRY POINT.  src/emu_io.h declares exactly one audio
hook, `void emu_dsky_beep(int duration_ms)`, and a duration is the whole of its
vocabulary - there is no way to hand a front end samples or a pitch through it.
so this is a DOWNSTREAM.md-sized change, not a local one: adding the hook is
the easy half and four ports implementing it is the rest.  a front end that
does not want it must keep working, so the new hook needs a default the way the
optional ones already here do.

docs/bug1.txt until 2026-09-15.  cpmdroid cannot close it alone.
