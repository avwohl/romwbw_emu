- with --escape=none there is no way into sim> from a running guest at all
(romwbw_emu.cc:203, :791).  that is the point of it, but it means the debugger
is reachable only by restarting with a different flag.  this is a product
choice, not a defect, and it is left here so it is decided rather than drifted
into.  what is on the table:
  - today: one reserved key, ^E by default (romwbw_emu.cc:160).  ^E is a
    WordStar cursor key, so the default costs a real keystroke in a real
    program, and --escape=none buys the key back by giving up the debugger.
  - the alternative: a two-key sequence, the escape char twice.  one press
    reaches the guest, two in a row reach sim>.  that gets both - the guest
    keeps every key that is not doubled, and --escape=none stops being the
    only way to get ^E back to WordStar.
  - what it would cost: the escape is one byte of state today
    (emu_console_check_escape, emu_io_cli.cc), and a two-key sequence needs a
    pending-escape state and a rule for what a lone escape followed by
    something else does - it has to be delivered late, so a guest polling
    CIOIN sees the first byte only after the second key arrives or a timeout
    expires.  DOWNSTREAM.md's emu_console_check_escape(char) contract is
    shared with three ports, so the shape of that state is theirs too.
  - and the reason it is still here rather than done: nobody has asked for it.
  the decision is whether a doubled escape replaces the single one, sits
  beside it, or is not worth the state.  nothing else in this file is blocked
  on it.

  - the whole aux/printer family (emu_printer_set_file, emu_printer_out,
  emu_printer_ready, emu_aux_set_input_file, emu_aux_set_output_file, emu_aux_in,
  emu_aux_out - emu_io.h:130-148, emu_io_cli.cc:479-554) still has no caller
  anywhere and no --printer flag to reach it.  the cleanup half is fixed:
  emu_io_cleanup() no longer fcloses them (emu_io_cli.cc:197-211), so the sim>
  escape can no longer end redirection for the run.  the rest is a decision,
  not work, and the measurement that makes it one:
    "LST:, PUN: and RDR: do nothing" was wrong.  they are ALIASED TO THE
    CONSOLE.  measured on hd1k_combo.img slice 0 under CP/M 2.2: `STAT DEV:`
    reports LST: is LPT: and PUN: is PTP:, `PIP LST:=SOURCE.TXT` prints the file
    on the terminal, `PIP PUN:=SOURCE.TXT` prints it on the terminal, and
    `PIP RD.TXT=RDR:` reads the console.  that is what happens because
    SYSGET_CIOCNT answers 1 (hbios_dispatch.cc:1671), so RomWBW's CBIOS has one
    character device to assign all four names to.
    so wiring emu_printer_out() up is not "add a flag".  it means answering 2
    to SYSGET_CIOCNT and routing CIO unit 1, which MOVES LST: and PUN: off the
    console - `PIP LST:=` stops printing on screen and `STAT DEV:` changes.
    that is a guest-visible change of behaviour for anyone using it today, and
    it is the owner's call whether the console alias or a real second device is
    the right answer.  deleting the family instead would take LST:/PUN:/RDR:
    away from nobody: they would keep working exactly as they do now.
  - emu_console_write_char does two things to every output byte, and both were
  measured rather than reasoned about this time.  driving the real
  emu_io_cli.o with the byte string "100%\rDONE\n" + the two UTF-8 bytes of an
  e-acute produced, byte for byte:
      1 0 0 %  D O N E \n  C )  8 - b i t \n
  which is the whole item in one line.  the CR is GONE, so "100%" and "DONE"
  ran together instead of one overwriting the other - a progress counter or a
  redrawn status line paints nothing.  and 0xC3 0xA9 came out as 'C' ')': the
  high bit is not stripped to leave the character mangled, it is stripped to
  leave a DIFFERENT, perfectly printable character.  8-bit output does not fail
  to arrive, it arrives as something else.
    this is a decision with a blast radius, which is why it is still here:
    - emu_io_cli.cc: keeping the CR would change piped output too, not just tty
      output.  OPOST/ONLCR only applies to a tty, so today a piped run yields
      bare LF and afterwards it would yield CR LF - every captured transcript
      and every script that greps the emulator's output changes.
    - emu_io_wasm.cc:184-190 has the identical two lines, and
      romwbw.html-template's Module.onConsoleOutput (:408) rewrites LF to CR LF
      specifically to undo the CR drop.  those two have to change in the same
      commit or xterm gets CR CR LF.  romwbw-debug.html has its own console
      handler and would need the same look.
    - the 0x7F mask is a separate question from the CR, and the answer is not
      mechanical: emu_io_cli.cc:137-144 records why it is there (WordStar sets
      bit 7 on the last character of a word and expects a dumb terminal to strip
      it), and against that stands every guest that draws a box or writes a
      national character.  the input side already clears ISTRIP to keep that
      same bit, so the asymmetry is real and deliberate on one side only.
    - and note what 1.36 did NOT achieve.  the changelog says the browser
      console "forwards every byte now"; that is true of Module.onConsoleOutput
      and false of the path as a whole, because emu_io_wasm.cc masks to 0x7F
      before the byte ever reaches JavaScript.  no high-bit byte can reach
      xterm today whatever the page does.

- handed over from z80cpmw, which suppresses it on its side: hbios_dispatch.cc
emits six C4267 warnings under MSVC at /W3.  All six are a size_t loop index
promoting a uint16_t guest address, where the truncation to sixteen bits IS the
Z80 64K wrap HBIOS wants, so there is nothing to fix today.  what makes it
actionable, exactly:
  - somebody adds /WX to the msvc job in .github/workflows/test.yml.  that job
    compiles these files at /W3 now, so the six are in this repo's own CI log
    from today; /WX turns them into a red build and the casts have to be
    written first.  the job deliberately does not use /WX for that reason.
  - or src/makefile turns on -Wshorten-64-to-32, which is the same class of
    warning from the other compiler.  cpmemu did that in its 9fee3c2 sweep and
    the sweep did not reach this file.
  either way the fix is a matching cast at each of the six, not a change of
  behaviour - the wrap is what HBIOS wants.

- found on a linux machine while doing the above, none of it planned:

  - the wbw_hd1k_0 diskdef cannot reach past 8 MB from the START of the image
  on any cpmtools built against libdsk, which is what debian and ubuntu ship
  and what CI installs.  disks/diskdefs records the measurement; the short
  version is that cpmtools' libdsk backend flattens (track, sector, offset)
  into one linear sector and bounds it by a geometry derived from `tracks`
  alone, so an 8 MB slice definition can only address the first 8 MB of the
  file it sits in.  slice 0 starts 1 MB in and holds 2000K today, so nothing
  has hit it; if r8.com or w8.com ever land in the last 1 MB of slice 0,
  disks/verify_disk_utils.sh will fail loudly rather than pass wrongly, which
  is the right way round but is still a surprise waiting to happen.  there is
  nothing to fix in this repository: cpmtools 2.23 cannot be configured
  without libdsk at all (./configure aborts with "No libdsk.h").  what would
  fix it upstream is a device_libdsk.c that seeks by offset instead of folding
  it into the linear sector number.

  - .claude/CLAUDE.md's cpmtools section has been corrected once for saying
  something that was true of homebrew and false of debian.  if it is edited
  again, check the claim on a debian machine before writing it: the upstream
  2.23 tarball ships 139 diskdefs and not one of them mentions RomWBW, so every
  wbw_* definition anywhere is a packager's addition.
