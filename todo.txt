- the IEXTEN item is closed on both sides, and the correction is worth keeping
because an earlier edit of this file got it wrong.  the clear cannot be proven
on linux - BSD/XNU gates VLNEXT (^V) and VDISCARD (^O) on IEXTEN alone, outside
the ICANON block, while on linux they sit inside it and are already off once
ICANON is - so it used to want a person at a mac.  it does not now.  here,
tests/cli_console.cc opens a pty and asserts ^V and ^O arrive.  cpmemu closed
its own copy in 55cc13f: src/os/linux/platform.cc:120 clears IEXTEN and
tests/pty_console.cc probes the platform and prints which bytes the clear is
saving, so the assertion says out loud whether it is testing anything.  nothing
is open here; do not re-file it.  the one thing to carry if the harness is
ported anywhere else: the failure shape is a timeout, not a wrong byte - VLNEXT
eats the ^V and then waits for the character it is meant to quote - so it needs
an alarm() guard or a regression hangs the suite instead of failing it.

- found while auditing the input path, none of it control-character work, all
of it out of scope for the commit that found it:
  - the wasm video/DSKY/sound callbacks are wired to names nothing implements:
  emu_io_wasm.cc emits Module.onVideo*/onDsky*, romwbw.html-template implements
  onVda*/onSnd*.  ~200 lines on both sides that have never executed, and
  Module.onError is dropped entirely, which is why nobody noticed.
  - the whole aux/printer family (printer_set_file, printer_out, printer_ready,
  aux_set_input_file, aux_set_output_file, aux_in, aux_out) has no caller
  anywhere.  LST:, PUN: and RDR: do nothing, and there is no --printer flag to
  reach them.  emu_io_cleanup() also fcloses them and emu_io_init() never
  reopens, so one press of the escape key would kill redirection for the run if
  it were ever wired up.
  - emu_console_write_char (emu_io_cli.cc:366-374) does two things to every
  output byte.  it drops every CR, not just the CR of a CR LF pair, so a guest
  returning to column 0 without a newline (progress counters, status line
  redraws) overwrites nothing - OPOST/ONLCR cannot restore a byte deleted before
  the tty saw it.  and the line above it, `ch &= 0x7F`, strips the high bit off
  everything, so 8-bit output never reaches the terminal at all.  the input side
  deliberately clears ISTRIP to preserve that same bit; the output side throws
  it away unconditionally.  same code in the wasm backend.
  - the web output filter (romwbw.html-template Module.onConsoleOutput) passes
  only 0x08, 0x0A, 0x1B and 0x20-0x7E, so TAB, BEL and FF never reach xterm.
  the CLI putchar()s them.  the ^R sweep in the other direction.
  - the disk selects in romwbw.html-template are worse than one bad entry.  they
  are a hardcoded five-name list fetched by bare relative filename, and only
  hd1k_combo.img exists in the repo - z80cpm_tools.img exists nowhere at all,
  and hd1k_infocom.img, which does exist, is described in the help text but
  never offered.  no deploy or package target copies any .img either, so a stock
  deb/rpm install 404s on both default disks and starts anyway.
  - the slice-count selects in romwbw.html-template call
  Module._romwbw_set_disk_slices, which does not exist: romwbw_web.cc defines
  no such entry point and it is not in EXPORTED_FUNCTIONS, so both selects
  silently do nothing.  the count is auto-derived from the number of loaded
  disks anyway, so the honest fix is probably to delete the two selects.
  - release.yml clones avwohl/cpmemu at default-branch HEAD with no tag or SHA
  to build libqkz80.a, and installs emsdk latest.  the second of those already
  broke a release once (13d1c23).

- found by sweeping z80cpmw's FEATURE_PARITY.md against this repo's source on
2026-08-24, row by row and each frontend separately.  eleven of its thirteen
rows were wrong about this repo, and four of the corrections are bugs here
rather than missing features:

  - both images in this repo now carry the new w8.com, but the ones it does not
  carry still ship the old one.  the web frontend's disk selects offer
  hd1k_cpm22.img, hd1k_games.img and z80cpm_tools.img, none of which exist
  anywhere on disk here, and the released hd1k_* assets live on a github
  release, so a user coming through either still gets the CWD-only W8.  the
  recipe, for whoever has those files:
    um80 -o w8.rel src/w8.asm && ul80 -o w8.com w8.rel
    cpmcp -f <diskdef> <image> w8.com 0:w8.com
  mind the diskdef - hd1k_combo.img is wbw_hd1k_0 because of its 1 MB MBR
  prefix, while the plain 8 MB hd1k_infocom.img is wbw_hd1k.  using the wrong
  one lists garbage rather than failing, which is how the infocom image was
  briefly and wrongly recorded as having no w8.com at all.
  - r8.com and w8.com in the images were not built the same way, and only one of
  them can be checked.  w8.com is a ul80 memory image: 256 leading NOPs, code at
  file offset 0x100, every address constant 256 higher to suit.  r8.com is a
  bare .COM with the code at offset 0.  Both run - CP/M loads either at 0100h
  and the NOPs slide into the code - but disks/verify_disk_utils.sh can only
  compare a same-layout pair, so it verifies w8 in both images and reports r8 as
  not comparable.  Whether r8.asm still corresponds to the shipped r8.com is
  therefore unknown; answering it needs either a relocating compare or a rebuild
  of r8.com in ul80's layout, and the second changes a working binary for no
  user-visible gain.  Deciding which layout these should be built in - and
  saying so somewhere - would make the check total.
  - the 256 NOPs in w8.com are waste, not design: ul80 emits from 0000h and
  nothing strips the pad.  1280 bytes of file to carry 1024 bytes of program,
  and the entry point runs 256 NOPs before reaching anything.  Harmless, and it
  is what the previous build did too, so the rebuild kept it rather than
  silently changing the shape of a shipped binary.

  - the web Boot field never reads NVRAM back.  it sets and clears through
  localStorage only, so a boot target the guest itself writes with SYSCONF is
  lost on reload - the CLI persists to $XDG_CONFIG_HOME/romwbw_emu/nvram and the
  web build has no equivalent read path.

  - the CLI has no way to clear a persisted boot target.  --boot= sets it and
  the file keeps it; a one-off --boot overwrites the saved value at exit, and
  there is no --boot=none or --clear-nvram to get back to the menu.
