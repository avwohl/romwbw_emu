- found by sweeping z80cpmw's FEATURE_PARITY.md against this repo's source, row
by row and each frontend separately.  what is left of it:

  - the disk images published outside this repo still carry old R8/W8.  both
  tracked images here are current and checked, but the released hd1k_* assets on
  github, the copies z80cpmw and cpmdroid bundle, and the 19 catalog entries in
  disks/disks.xml that exist nowhere in this tree are all whatever they were
  built with.  a user coming through any of those gets a W8 that truncates every
  binary at the first 1Ah and an R8 that can erase files it did not create.
  refreshing them means rebuilding the image and cutting a release the catalog
  points at; the build half is disks/rebuild_disk_utils.sh now, not prose.
  worth noting what would make this catchable rather than periodic: disks.xml
  carries no per-disk version or checksum, so nothing here can look at a release
  asset and tell whether its w8.com is current.

  - the web Boot field never reads NVRAM back.  romwbw.html-template pushes it
  to the core (_romwbw_set_boot_string, :1160-1170), clears it
  (_romwbw_clear_nvram, :1192-1200) and persists the text in localStorage only;
  there is no getter in EXPORTED_FUNCTIONS (web/makefile:21), so a boot target
  the guest itself writes with SYSCONF is lost on reload.  the CLI persists to
  $XDG_CONFIG_HOME/romwbw_emu/nvram (romwbw_emu.cc:75-108) and the web build has
  no equivalent read path.

  - the CLI has no way to clear a persisted boot target.  --boot= sets it and
  the file keeps it; there is no --boot=none or --clear-nvram to get back to the
  menu.  the operation exists in the web core already - romwbw_clear_nvram(),
  web/romwbw_web.cc:171 - so this is a flag and a call, and --escape already has
  the "none" spelling to copy (parse_escape_char, romwbw_emu.cc:166-199).
    the consequence worth drawing out, hit repeatedly while testing W8: a
    one-off --boot is saved at exit (romwbw_emu.cc:1613-1619), so ANY automated
    run that boots the emulator rewrites the developer's persisted boot target
    as a side effect.  a --boot given on the command line should be an override
    for that run and skip the save; separately, anything scripted should point
    XDG_CONFIG_HOME at a temp directory.

- handed over from z80cpmw, which suppresses it on its side: hbios_dispatch.cc
emits six C4267 warnings under MSVC at /W3.  All six are a size_t loop index
promoting a uint16_t guest address, where the truncation to sixteen bits IS the
Z80 64K wrap HBIOS wants, so there is nothing to fix today - but a matching cast
is worth adding if this repo ever turns C4267 or -Wshorten-64-to-32 on for
itself.  cpmemu's 9fee3c2 sweep for this class did not reach this file.

- left open by the W8 host-path work (docs/DOWNSTREAM_2026-08-25.md), each
measured and deliberately not taken:

  - R8's "Reading:" line still prints the path the CCP shouted rather than the
  file that was opened.  W8 asks the emulator (HBF_HOST_GETNAME) because for a
  write the two are never the same string; for a read they usually are, the file
  has to exist for the open to succeed, and there is no getter for the read name
  in the emu_io contract.  Adding one is a mirror of 0xE8 and about the same
  size.  It is the same class of untruth, one consequence smaller: nothing is
  created that the user then has to find.

  - emu_host_file_open_write() returns true unconditionally on every buffering
  backend (browser, iOS, Android, and z80cpmw's deferred write), so a path that
  cannot be created is only discovered at close - and W8 then prints "Host file
  close failed - file may be truncated" for a file that was never opened.  The
  contract in emu_io.h now says this is allowed and that close is where the real
  answer comes from; making W8's two messages tell the cases apart would need a
  distinguishable status from close, which is a wider change than it looks.

  - HBF_HOST_OPEN_R and HBF_HOST_OPEN_W read at most 256 bytes of guest memory
  looking for a terminator and silently use what they have
  (hbios_dispatch.cc:2391, :2413).  Both utilities NUL-terminate inside a
  128-byte buffer so nothing can reach it today; it is a truncation rather than
  an overrun, and it would matter to a guest program that is not R8 or W8.

  - W8 treats any nonzero F_READ status as a clean end of file (w8.asm:145).
  Under CP/M 2.2 the only nonzero code is 1, EOF, so this is exact there; under
  ZSDOS and CP/M 3 a real read error would be reported as a successful export of
  everything up to it.

  - src/makefile's sister-directory qkz80 fallback (lines 15-21) is silent, so a
  machine with neither pkg-config nor ../../cpmemu falls through to /usr/local
  and compiles a different CPU core with no indication.  test.yml passes
  QKZ80_CFLAGS/QKZ80_LIBS explicitly to sidestep it; a warning in the makefile
  would be better than a workaround in one caller.

  - W8's and R8's error messages still echo the path the CCP shouted:
  "Error: Cannot create host file: /NODIR/X.COM".  That is the request rather
  than a claim about what exists, so it is not the same defect the success line
  had - but the two now differ in case for no reason a user can see.

  - emu_host_path_basename puts no length cap on what it returns, so a 5000-
  character last component becomes a 5000-character suggested download name.
  Every caller is a filename hint and no filesystem will take it; harmless
  today, and a cap would want to keep the extension rather than the head.

  - cpmrm exits 0 on a read-only image without removing anything, so
  disks/rebuild_disk_utils.sh attributes the resulting failure to cpmcp rather
  than to the permissions.  The run does fail, it just says the wrong thing.
