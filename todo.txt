- found by sweeping z80cpmw's FEATURE_PARITY.md against this repo's source, row
by row and each frontend separately.  what is left of it:

  - both images in this repo carry the new w8.com; the ones it does not carry
  still ship the old one.  the web frontend's disk selects offer hd1k_cpm22.img,
  hd1k_games.img, hd1k_zsdos.img and z80cpm_tools.img, none of which exist
  anywhere on disk here, and the released hd1k_* assets live on a github
  release, so a user coming through either still gets the CWD-only W8.  the
  recipe, for whoever has those files:
    um80 -o w8.rel src/w8.asm && ul80 -o w8.com w8.rel
    cpmcp -f <diskdef> <image> w8.com 0:w8.com
  mind the diskdef - hd1k_combo.img is wbw_hd1k_0 because of its 1 MB MBR
  prefix, while the plain 8 MB hd1k_infocom.img is wbw_hd1k.  using the wrong
  one lists garbage rather than failing.

  - decide which layout r8.com and w8.com should be built in, and say so
  somewhere; that is what would make disks/verify_disk_utils.sh total.  w8.com
  is a ul80 memory image - 256 leading NOPs, code at file offset 0x100, every
  address constant 256 higher to suit - while r8.com is a bare .COM with the
  code at offset 0.  Both run, because CP/M loads either at 0100h and the NOPs
  slide into the code, but the script can only compare a same-layout pair, so it
  verifies w8 in both images and reports r8 as not comparable.  Whether r8.asm
  still corresponds to the shipped r8.com is therefore unknown; answering it
  needs either a relocating compare or a rebuild of r8.com in ul80's layout, and
  the second changes a working binary for no user-visible gain.  Note the 256
  NOPs are waste rather than design - ul80 emits from 0000h and nothing strips
  the pad, so it is 1280 bytes of file to carry 1024 bytes of program - and the
  rebuild kept them rather than silently changing the shape of a shipped binary.

  - the web Boot field never reads NVRAM back.  romwbw.html-template pushes it
  to the core (_romwbw_set_boot_string, :1160-1170), clears it
  (_romwbw_clear_nvram, :1192-1200) and persists the text in localStorage only;
  there is no getter in EXPORTED_FUNCTIONS (web/makefile:21), so a boot target
  the guest itself writes with SYSCONF is lost on reload.  the CLI persists to
  $XDG_CONFIG_HOME/romwbw_emu/nvram (romwbw_emu.cc:75-108) and the web build has
  no equivalent read path.

  - the CLI has no way to clear a persisted boot target.  --boot=
  (romwbw_emu.cc:1072) sets it and the file keeps it; a one-off --boot
  overwrites the saved value at exit (romwbw_emu.cc:1613-1619), and there is no
  --boot=none or --clear-nvram to get back to the menu.  the operation exists in
  the web core already - romwbw_clear_nvram(), web/romwbw_web.cc:171 - so this
  is a flag and a call, and --escape already has the "none" spelling to copy
  (parse_escape_char, romwbw_emu.cc:166-199).
