  - the whole aux/printer family (emu_printer_set_file, emu_printer_out,
  emu_printer_ready, emu_aux_set_input_file, emu_aux_set_output_file, emu_aux_in,
  emu_aux_out - emu_io.h, emu_io_cli.cc) still has no caller anywhere and no
  --printer flag to reach it.  the cleanup half is fixed: emu_io_cleanup() no
  longer fcloses them, so the sim> escape can no longer end redirection for the
  run.  the rest is a decision, not work, and the measurement that makes it one:
    "LST:, PUN: and RDR: do nothing" was wrong.  they are ALIASED TO THE
    CONSOLE.  measured on hd1k_combo.img slice 0 under CP/M 2.2: `STAT DEV:`
    reports LST: is LPT: and PUN: is PTP:, `PIP LST:=SOURCE.TXT` prints the file
    on the terminal, `PIP PUN:=SOURCE.TXT` prints it on the terminal, and
    `PIP RD.TXT=RDR:` reads the console.  that is what happens because
    SYSGET_CIOCNT answers 1 (hbios_dispatch.cc), so RomWBW's CBIOS has one
    character device to assign all four names to.
    so wiring emu_printer_out() up is not "add a flag".  it means answering 2
    to SYSGET_CIOCNT and routing CIO unit 1, which MOVES LST: and PUN: off the
    console - `PIP LST:=` stops printing on screen and `STAT DEV:` changes.
    that is a guest-visible change of behaviour for anyone using it today, and
    it is the owner's call whether the console alias or a real second device is
    the right answer.  deleting the family instead would take LST:/PUN:/RDR:
    away from nobody: they would keep working exactly as they do now.
  - emu_console_write_char does two things to every output byte, and both were
  measured rather than reasoned about this time.  driving the real
  emu_io_cli.o with the byte string "100%\rDONE\n" + the two UTF-8 bytes of an
  e-acute produced, byte for byte:
      1 0 0 %  D O N E \n  C )  8 - b i t \n
  which is the whole item in one line.  the CR is GONE, so "100%" and "DONE"
  ran together instead of one overwriting the other - a progress counter or a
  redrawn status line paints nothing.  and 0xC3 0xA9 came out as 'C' ')': the
  high bit is not stripped to leave the character mangled, it is stripped to
  leave a DIFFERENT, perfectly printable character.  8-bit output does not fail
  to arrive, it arrives as something else.
    this is a decision with a blast radius, which is why it is still here:
    - emu_io_cli.cc: keeping the CR would change piped output too, not just tty
      output.  OPOST/ONLCR only applies to a tty, so today a piped run yields
      bare LF and afterwards it would yield CR LF - every captured transcript
      and every script that greps the emulator's output changes.
    - emu_io_wasm.cc has the identical two lines, and romwbw.html-template's
      Module.onConsoleOutput (:407) rewrites LF to CR LF specifically to undo
      the CR drop.  those two have to change in the same commit or xterm gets
      CR CR LF.  romwbw-debug.html has its own console handler and would need
      the same look.
    - the 0x7F mask is a separate question from the CR, and the answer is not
      mechanical: emu_io_cli.cc:139-145 records why it is there (WordStar sets
      bit 7 on the last character of a word and expects a dumb terminal to strip
      it), and against that stands every guest that draws a box or writes a
      national character.  the input side already clears ISTRIP to keep that
      same bit, so the asymmetry is real and deliberate on one side only.
    - and note what 1.36 did NOT achieve.  the changelog says the browser
      console "forwards every byte now"; that is true of Module.onConsoleOutput
      and false of the path as a whole, because emu_io_wasm.cc masks to 0x7F
      before the byte ever reaches JavaScript.  no high-bit byte can reach
      xterm today whatever the page does.

- left open by the W8 host-path work (docs/DOWNSTREAM_2026-08-25.md), each

  0xEA), but only on the CLI.  emu_io_wasm.cc's emu_host_file_get_read_name()

  - emu_host_file_open_write() returns true unconditionally on every buffering
  backend (browser, iOS, Android, and z80cpmw's deferred write), so a path that

  contract in emu_io.h now says this is allowed and that close is where the real
  answer comes from; making W8's two messages tell the cases apart would need a
  distinguishable status from close, which is a wider change than it looks.
